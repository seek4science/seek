# WorkflowHub on AWS: next phase

What is needed to take the Pulumi program in
[`infra/biofair-mc-workflow-hub/`](../infra/biofair-mc-workflow-hub/) from
phase 1, through phase 2 (staging), phase 3 (protecting the data, and sizing)
and phase 4 (post-staging), to the full design in
[`SEEK-pulumi-handover.md`](SEEK-pulumi-handover.md).

The Pulumi project in `infra/biofair-mc-workflow-hub/`, on the SEEK
repository's `pulumi` branch, is the authoritative copy; biofair-mc-infra's
`biofair-mc-workflow-hub/` holds a copy of it. Make changes here and copy them
across.

## Where phase 1 stands

Phase 1 is the managed-services design with the extras left out, and with the
front-end and workers as Docker containers on EC2 Auto Scaling groups rather
than ECS Fargate. It was deployed in the `biofair-mc-workflow-hub`
account, paused and resumed with its data intact, and destroyed cleanly. It
needs no IAM permissions beyond the `Developer` permission set. All seven
phase 2 items have since been completed, and are marked below; only the Solr
volume's scheduled snapshots wait, on an IAM role from the Hub. Phase 3's
first two items, the data and compute stacks and protecting the data, are
complete too, and the web tier has been sized and its scaling load tested.

The full design, before phase 1 cut it down, is in the history at commit
`6550a42c0b`. Most items below were already written there and can be adapted
rather than written from scratch:

```console
git show 6550a42c0b:infra/biofair-mc-workflow-hub/Pulumi.yaml
```

Resource names in this document (`dnsRecord`, `solrData` and so on) refer to
that file. When bringing any of it back, keep the fixes phase 1 found: VPC
DNS hostnames, explicit lowercase names for the RDS and ElastiCache groups,
gp3 database storage, and `-sg` security group names.

## Phase 2 items

Roughly in order of value. Each says what it adds, what it needs, and anything
that blocks it.

### 1. **Completed:** HTTPS with a self-signed certificate

- **Adds:** HTTPS at the load balancer's own hostname, for testing. Browsers
  warn about the certificate, but the connection is encrypted.
- **Done as:** a key and self-signed certificate generated by Pulumi's `tls`
  provider (`tlsKey`, `tlsCert`), named `<prefix>.seek.internal` because the
  load balancer only accepts certificates for a fully qualified domain name,
  and imported into ACM (`certificate`). The load balancer has a 443 listener
  using it, port 80 redirects to it, and `albSg` allows 443. The listener and
  redirect carried over unchanged when phase 4 swapped in a certificate from
  ACM for the site's domain.

### 2. **Completed:** Private DNS name for Solr

- **Adds:** `solr.seek.internal` instead of the instance's IP in the SEEK
  environment, so replacing Solr does not need the web and worker instances
  rolled.
- **Done as:** a Route 53 private zone attached to the VPC (`internalZone`),
  an A record for the Solr instance (`solrRecord`), and
  `SOLR_HOST=solr.seek.internal` in `hostSetup`.

### 3. **Completed:** Front-end autoscaling

- **Adds:** 1-8 web instances, scaled on CPU (six for now, the vCPU quota;
  scaling on requests and response time came later, item 4 of phase 3).
- **Done as:** `webGroup` runs between `webCount` and `webCountMax`, with no
  desired capacity set, so autoscaling owns it; `webScalePolicy`, a target
  tracking policy on `ASGAverageCPUUtilization` at `webCpuTarget` (50%, low
  because a new instance takes about five minutes to boot and pull the
  image); and a 300-second instance warm-up. Tested under load: the group
  scaled out to three instances, and scaled back in once the load stopped.
- **Consider:** detailed monitoring on the web launch template
  (`monitoring: enabled: true`, about $2 a month per instance). With basic
  monitoring CPU is reported every five minutes, so scaling reacts late in
  both directions, and can add an instance as load ends.

### 4. **Completed:** Shared file cache

- **Adds:** a `tmp/cache` shared between web instances, so a large generated
  file is not regenerated per instance (handover 3.3).
- **Done as:** `cacheAccessPoint`, a second access point on the EFS
  filesystem at `/cache`, owned by uid 33; `hostSetup` mounts it at
  `/mnt/cache` alongside the filestore; and both the web and worker
  `docker run` mount it as `/seek/tmp/cache`, as docker-compose does, so the
  workers' cleanup job prunes the shared cache.

### 5. **Completed:** Redis auth token

- **Adds:** a password on Redis, on top of TLS and the security group. Redis
  holds SEEK's sessions, so anything that could reach it could take over or
  alter a logged-in user's session. Today only the web, worker and Solr
  instances can reach it, and they already hold the database password, so
  this guards against a later loosening of the security groups more than
  against anything possible now. It also matches docker-compose, which sets a
  Redis password.
- **Done as:** `redisAuthToken`, a `random:RandomPassword` of 32 letters and
  digits generated by the program and held as a secret in the state; the
  token in Parameter Store as a SecureString (`redisAuthTokenParam`), read in
  `hostSetup` and written as `REDIS_PASSWORD` to `/etc/seek.env`, which
  `Seek::RedisConfig` already reads; and `authToken` on the replication
  group. A token set at creation is required from the start, but changing
  it in place uses `ROTATE`, which leaves it optional (and adding one where
  there was none still admits clients without it) until a separate `SET`.
  So `replaceOnChanges: ["authToken"]` replaces the group whenever the token
  changes, logging users out and emptying the cache. Tested: connections
  without the token or with a wrong one are refused, and SEEK's cache and
  sessions work.

### 6. **Completed:** Security groups and secure connections

- **Adds:** a review of what can reach what inside the VPC, and of which
  connections between components are encrypted.
- **Done: Solr isolated.** Solr has its own security group, `solrSg`,
  admitting only 8983 from the web and worker instances (`appSg`); it no
  longer shares `appSg`, so `dataSg` no longer admits it, and Solr cannot
  reach the database, Redis or EFS. Tested: search works, and a connection
  from the Solr instance to MySQL is refused.
- **Done: MySQL over TLS.** The instances download the RDS CA bundle at
  boot and set `MYSQL_SSL_CA` (handover change 5.2), so Rails and the
  entrypoint's checks connect over TLS and verify the server's certificate,
  and `dbParams` sets `require_secure_transport`, so RDS refuses plain
  connections. Tested: a plain connection is refused, and SEEK and the
  workers run.
- **Done: load balancer to web instances over HTTPS.** The web containers
  run with `NGINX_TLS` (handover change 5.5), so nginx serves HTTPS on 3000
  with a self-signed certificate generated at each start; the target group
  and its health check use HTTPS. The load balancer does not verify target
  certificates, so nothing needs distributing or renewing. Tested: the
  target is healthy over HTTPS, the site works, and nginx answers TLSv1.3
  on 3000 and refuses plain HTTP there.
- **Connections now:** all encrypted: browser to load balancer and load
  balancer to web instances (HTTPS), and instances to MySQL, Redis, Solr
  (TLS) and EFS (the mount helper's `tls` option).
- **Done: Solr over TLS.** Unlike the load balancer, SEEK verifies Solr's
  certificate. The program generates a key and a self-signed certificate
  for `solr.seek.internal` and `localhost` (`solrTlsKey`, `solrTlsCert`),
  valid ten years and renewed by a `pulumi up` in the last; the key is in
  Parameter Store, read at boot into a PKCS12 keystore for Solr's
  `SOLR_SSL_*` settings. The web and worker instances trust the certificate
  itself through `SSL_CERT_DIR`, which leaves the image's public CAs in
  place, and Sunspot uses an `https` `SOLR_URL`. The Solr image's health
  check follows the TLS setting (handover change 5.6). A change to the Solr
  user data now replaces the instance (`userDataReplaceOnChange`), since
  user data only runs on first boot. Tested: HTTPS verified, plain HTTP and
  other certificates refused, search works, and a full reindex indexed every
  searchable item; indexing during the rollout was lost, as expected, and
  the reindex restored it.

### 7. **Completed:** Durable Solr index

- **Adds:** an index that survives the Solr instance being replaced, so a
  replacement does not mean a full reindex (handover 3.6).
- **Done as:** `solrData`, a gp3 volume of `solrDataSizeGb` (20 GB; a
  production index measured 7.4 GB, and Solr needs about twice the index
  size while merging or reindexing), placed in the Solr subnet's AZ by the
  `solrSubnet` lookup; `solrAttach`, which stops the instance before any
  detach; and Solr user data that finds the volume by its ID, waits for it to
  attach, formats it only if it is blank, and mounts it at `/var/solr` by
  UUID. The Solr instance and the attachment use `deleteBeforeReplace`: the
  volume can only be attached to one instance, so a replacement must detach
  it and delete the old instance before creating the new one. Tested by
  replacing the Solr instance: the same volume was reattached unformatted,
  and the index and search were intact.
- **Still open: snapshots.** Nightly snapshots (the full design's `dlmRole`
  and `solrSnapshots`) need `AWSDataLifecycleManagerDefaultRole`, which does
  not exist in the account, and permission for `Developer` to pass it to
  `dlm.amazonaws.com`, which it lacks. Both need the Hub. Until then, take a
  one-off snapshot before risky changes (`aws ec2 create-snapshot`), and
  rely on a reindex from MySQL if the volume is lost.
- **Resizing:** the volume can grow in place with `pulumi up` after raising
  `solrDataSizeGb` (at most once every six hours), followed by `resize2fs`
  on the Solr instance; it cannot shrink.

## Phase 3: protecting the data, and sizing

### 1. **Completed:** Data and compute stacks

- **Adds:** a `pulumi destroy` of the compute that cannot touch the database,
  filestore or Solr index, and a cheaper way to take the deployment down
  between uses: with the compute destroyed and the database stopped, only
  storage is billed, about $0.02 an hour, against $0.15 an hour for the old
  pause, which could not stop the NAT gateway, load balancer or ElastiCache.
- **Done as:** two Pulumi projects under `infra/biofair-mc-workflow-hub/`,
  each with a `staging` stack:

  | `data/` (long-lived) | `compute/` (disposable) |
  |---|---|
  | VPC and subnets (`awsx`, `natGateways: None`) | NAT gateway and Elastic IP, and a default route through it in each private route table |
  | Security groups (`albSg`, `appSg`, `solrSg`, `dataSg`), which reference each other | Redis, its auth token and parameter |
  | RDS, its subnet and parameter groups, the password parameter | Solr instance, attachment, TLS key and certificate, DNS record |
  | EFS, mount targets and access points | Load balancer and its certificate |
  | The private DNS zone | Web and worker launch templates and groups, scaling policy |
  | The Solr data volume | |

  The compute stack reads the data stack's outputs through a
  `pulumi:pulumi:StackReference` to the data stack of the same name. It looks
  up the private route tables by subnet itself, since in the data stack the
  lookup could run before `awsx` associates the subnets with their tables,
  and the Solr instance and both groups depend on its NAT routes, so nothing
  boots before it can pull its image. `namePrefix` is set explicitly, so
  resource names are unchanged.
- **Found:** with the local backend, the stack reference has to open the
  data stack's state, and cannot prompt for its passphrase: both stacks need
  the same passphrase, given through `PULUMI_CONFIG_PASSPHRASE(_FILE)`.
- **Tested:** both stacks deploy on staging, and the site, Solr and MySQL over
  TLS, Redis and the workers work; destroying and recreating the compute
  stack keeps the database, the filestore and the Solr index.
- **Later, for production:** a deployment that already holds data would move
  its live resources between stacks with Pulumi's state tools (`pulumi state
  move`) rather than redeploying; staging was simply rebuilt.

### 2. **Completed:** Protect the database, EFS and the Solr volume

- **Adds:** Pulumi refuses to delete the RDS instance, the EFS filesystem or
  the Solr volume; a `destroy` or a change that would replace them fails
  instead. This guards the data inside Pulumi, alongside RDS's own deletion
  protection, and covers EFS and EBS, which have no protection of their own.
- **Done as:** `options: protect: ${protectData}` on `db`, `sharedFs` and
  `solrData` in the data stack; `protectData` defaults to true, and the
  staging config turns it off so staging can be torn down completely, as
  with `dbDeletionProtection`. Removing protected resources needs
  `protectData` set to false and a `pulumi up` first.
- **Checked:** a preview sets `protect` with `protectData` true and leaves it
  unset with false. A `destroy` refused by protection on staging is still to
  be tried.

### 3. Review instance types and sizes (web tier done)

- **Adds:** sizes based on measured use rather than estimates, before the
  deployment holds real data and costs start to matter.
- **Done for the web tier**, by load testing staging with k6, requests
  arriving at a set rate so they overlap as SEEK slows:
  - One `t3.large` with four Puma workers serves about 5-6 page views a
    second (about 350 requests a minute) before response times climb, with
    both vCPUs saturated and 2 GB of 7.6 used. More workers would add memory
    use but not throughput; more throughput per instance needs more CPU
    (`c7i`/`m7i`), and two `t3.large` cost less than one `m7i.xlarge`.
  - `webPumaWorkers` (default 2) is now stack config, set to 4 for staging,
    and `webRequestTarget` is 250, about 70% of the measured limit.
  - The account's quota for standard instances is 16 vCPUs, which caps
    staging at six web instances (`webCountMax` 6); an increase to 32 has
    been asked of the Hub.
- **Still open:** the worker, Solr, RDS and ElastiCache sizes under real
  use; the Solr JVM memory as config (`SOLR_JAVA_MEM` is fixed in the Solr
  user data); reserved instances or a savings plan once sizes settle.
  Graviton (`t4g`, `m7g`) is cheaper, but needs arm64 builds of the SEEK
  and Solr images (the SEEK Dockerfile fetches an amd64 supercronic), and
  `db.t4g` classes are not offered in the VPC's zones.

### 4. Scaling on more than CPU (partly done)

- **Done:**
  - Target tracking on the load balancer's requests per instance
    (`webRequestTarget`) alongside CPU, and step scaling on a two-minute
    request surge and on slow responses (`webResponseTimeLimit`).
  - Detailed monitoring on the web instances, so CPU is reported every
    minute.
  - Found by load testing, and fixed: the health check replaced overloaded
    instances after 2.5 minutes (now five minutes of failures); rebalancing
    across zones terminated the one instance serving traffic (now
    `NewestInstance`); requests were dealt round-robin to overloaded
    instances (now `least_outstanding_requests`).
  - Result: a surge to three times one instance's capacity reached six
    instances and 0.3 s median responses with no instance lost, but took
    about seven minutes to the first new instance serving: three and a half
    to notice (CPU is the fastest signal; the load balancer's request counts
    arrive later) and four to boot.
- **Still open, roughly in order of value:**
  - **Faster boots.** Installing packages and pulling the SEEK image take
    two and a half of a new instance's four minutes. A prepared AMI with
    Docker, the EFS helper and the image would save most of that (about
    $0.50 a month per image version kept; one per SEEK release, and needs
    `ec2:CreateImage`). A warm pool of stopped instances would make a scale
    out about a minute (about $2.80 a month each, for the disk), but user
    data only runs on first boot and Auto Scaling may stop an instance
    before it finishes, and the instance role cannot complete a lifecycle
    hook; it needs the setup moved into a service that runs, safely, at
    every boot.
  - **A minimum of two web instances**, at least in working hours (a
    scheduled action), so one overloaded or replaced instance never leaves
    none healthy; about $0.10 an hour.
  - **Load shedding:** limit each instance's queue in nginx (`limit_conn`,
    answering 503 at a few times the Puma worker count), so excess requests
    fail fast rather than waiting 60 s and exhausting connections. A SEEK
    change to `docker/nginx.conf.template`; `/up` must not be shed.
  - **Predictive scaling** once there is real traffic to learn from.
  - **Scaling on Puma's own fullness** (busy workers and backlog, from its
    control app) would measure capacity directly, but publishing it needs
    `cloudwatch:PutMetricData` on the instance role, which the Hub manages:
    the same request as container logs (phase 4).

## Phase 4 (post-staging)

For once the deployment moves beyond staging.

### 1. **Completed:** A real domain

- **Adds:** a real hostname and a certificate browsers trust, replacing the
  self-signed one the program generated.
- **Done as:** `domainName` in the data stack (`wfh.fairdom-seek.org` for
  staging), whose DNS is delegated from the parent domain (`fairdom-seek.org`,
  at GoDaddy) to a public Route 53 zone in the data stack (`publicZone`),
  through NS records for `wfh` there. The data stack also holds the ACM
  certificate (`siteCertificate`), validated by a record in that zone that
  also lets ACM renew it, and waits until it is issued
  (`siteCertificateValidation`). The compute stack's 443 listener uses that
  certificate, and an alias record (`siteRecord`) points the domain at the
  load balancer, whose name changes whenever the compute is recreated.
  Delegating to Route 53 means nothing at GoDaddy changes after the NS
  records are added, however often the compute is redeployed; records set
  by hand there would need updating each time.
- **Deploying:** two passes, since validation waits for the delegation:
  create the zone alone (`pulumi up --target` its URN), add its name servers
  as NS records at GoDaddy, then `pulumi up` the data stack and the compute
  stack. Then set the site's base host in SEEK's admin settings.
- **Tested:** on staging, `https://wfh.fairdom-seek.org` resolves through the
  delegation to the load balancer and serves with the ACM certificate
  (issued by Amazon, renewed automatically); HTTP redirects to HTTPS.
- **Production:** the same, with the production domain, once its DNS and
  who issues its certificate are agreed with the Hub.

### 2. Database and EFS backups

- **Database now:** RDS automated backups are on (`backupRetentionPeriod:
  14`): a daily snapshot plus point-in-time recovery to any second in the
  last 14 days. But they belong to the database instance: deleting it
  deletes them, and the staging config also skips the final snapshot
  (`dbSkipFinalSnapshot`), so a staging `destroy` leaves nothing. They are
  also in the same account and region as the database.
- **Database for production:**
  - keep the defaults, deletion protection on and a final snapshot taken on
    deletion;
  - decide the retention (up to 35 days for automated backups; longer needs
    manual or AWS Backup snapshots);
  - consider copies outside the account or region (AWS Backup cross-region
    or cross-account copy), which need an AWS Backup service role from the
    Hub;
  - consider regular logical dumps (`mysqldump`) to S3, which restore into
    any MySQL, not only RDS, and make moving the data elsewhere simple.
- **EFS:** the filestore holds the uploaded files, so needs backing up as
  much as the database. The full design's `efsBackup` turns on EFS automatic
  backups, which use AWS Backup and its service role.
- **Check:** whether `Developer` can enable EFS automatic backups and AWS
  Backup plans. AWS Backup's default service role does not exist in the
  account, and passing roles is likely denied, as it is for snapshots
  (phase 2 item 7), so this may need the Hub too.
- **Test:** restore both, the database to a point in time and a file from
  EFS, before relying on them.

### 3. Container logs in CloudWatch

- **Adds:** Rails, Puma and worker logs in the console, kept after an
  instance is replaced.
- **Needs:** CloudWatch Logs permissions for the instances, and either the
  `awslogs` Docker log driver or the CloudWatch agent. The existing SSM
  instance profile does not include them, so this needs the Hub: extra
  permissions on that profile, or a second profile the program can use.

### 4. Higher availability

A NAT gateway per AZ (in the compute stack, each private subnet routing
through its own AZ's), Multi-AZ RDS, an ElastiCache
replica with automatic failover, and Solr in an Auto Scaling group of one.
Each roughly doubles the cost of that part.

### 5. Email delivery

- **Adds:** working email from SEEK: account activation and password
  resets, subscription and other notifications, and error reports.
- **Needs:** an SMTP server for SEEK's settings (`email_enabled`, the `smtp`
  settings and `noreply_sender`, set in SEEK's admin pages, not in the
  program). Either:
  - **Amazon SES** in `eu-west-2`: verify the sending domain with DNS
    records (DKIM), so it follows the real domain (item 1); request
    production access to leave the SES sandbox, which only delivers to
    verified addresses; and create SMTP credentials, which are an IAM user's
    keys, so need the Hub. Held in Parameter Store, read at boot as the
    database password is.
  - **An existing institutional relay**, if one will accept mail from AWS.
- **Notes:** EC2 blocks outbound port 25 by default; use the submission
  port (587) with STARTTLS, which the instances can already reach through
  the NAT gateway.

## Cross-cutting work

- **Shared Pulumi state backend.** S3 or Pulumi Cloud, agreed with
  biofair-mc-infra, before anyone other than the first deployer manages the
  stack.
- **Generate secrets in the program.** The Redis token already is
  (`random:RandomPassword`); do the same for the database password, letters
  and digits only, so the stack config holds no secrets and nobody chooses
  one by hand.
- **Secrets provider for the shared state.** Secrets in the state (the
  database password, the Redis token, the certificate's private key) are
  encrypted with the deployer's passphrase; a shared backend needs a
  secrets provider others can use, such as a KMS key or Pulumi Cloud.
- **SEEK on a shared `tmp/cache`.** The web and worker processes on every
  instance share the file cache on EFS, and two SEEK problems show up (see
  the tech notes): i18n-js's development middleware, registered in every
  environment, deletes `tmp/cache/i18n-js.yml` whenever a Puma worker
  starts, causing occasional 500s (fix: register it in development only);
  and Rails' file cache store fails walking directories other processes
  remove (fix: tolerate vanished directories). Both are SEEK changes, and
  the second also affects single-server deployments.
- **Requests to the Hub,** collected: a vCPU quota for standard instances of
  32 rather than 16 (asked); CloudWatch permissions on the instance role
  (`cloudwatch:PutMetricData`, CloudWatch Logs) for container logs, memory
  and Puma metrics; IAM roles for scheduled snapshots of the Solr volume and
  for database and EFS backups; DNS and certificates for a production
  domain.
- **VPC ownership.** Whether the Hub provides networking, in which case the
  program's VPC is replaced by lookups.
- **A production stack** once a production account exists, with deletion
  protection and final snapshots on (the defaults).

## Fargate (deferred)

The `pulumi-fargate-phase-1` branch has phase 1 on ECS Fargate instead of
Auto Scaling groups, with the fixes its preview found, including the
execution role's read access to the database secret. It needs:

- two IAM roles trusted by `ecs-tasks.amazonaws.com`: an execution role with
  the AWS-managed `AmazonECSTaskExecutionRolePolicy` plus
  `secretsmanager:GetSecretValue` on the database secret, and a task role;
- permission for the deployer to pass those roles to ECS on every deploy
  that changes a task definition.

`Developer` cannot create IAM roles or pass them to ECS, so this needs the
roles and that permission from the Hub, or a permission set that has them.
The program would then take the role ARNs as config rather than creating
them. That branch also predates phase 1's VPC DNS hostnames and gp3 fixes.
